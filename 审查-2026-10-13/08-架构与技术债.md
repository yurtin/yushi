## 一、这个项目在架构上实际长什么样

### 大白话

一个 19,574 行的网页文件，前面 4,142 行是衣服（样式），中间 258 行是骨架（页面标记），后面 15,170 行是全部逻辑。逻辑不分成文件，而是靠注释划线分成二十来块：先是一块"认字"的（把一句话拆成标题、日期、标签），然后是一块"记账"的（存进 localStorage、读出来），再往上是一屏一屏的画法、点击、弹窗。外面还套着一个安卓壳，壳里又有 1,740 行 Java 管通知、录音、选图、响铃。

### 专业叫法

**单文件分层架构（layered monolith in a single file）**，模块边界用注释标记而不是语言结构。依赖图是"上层调下层"的经典形状，加上一条外壳层与页面层之间的双向桥。

专业上判断这种结构健康与否，看的不是"文件多不多"，而是三件事：**依赖箭头方向是否一致**（Clean Architecture 的 ADP/DIP）、**同一件事有没有多处表述**（Pragmatic Programmer 的 DRY，指决策而不是代码行）、**一层是不是只有一个职责**（Ousterhout 的深模块）。

### 为什么值得知道

单文件不是问题，这个项目自己也把"单文件、无构建"列为既定形态。问题在于：当二十来个"层"共享一个全局命名空间、一个全局数据对象、一个全量重绘函数时，**改动的传播半径不是由你改的那一行决定的，而是由总线和全局状态决定的**。这正是下面 R2 那一组发现的来源。

## 三、R1 认知负载

> **这一段在说什么。** 大白话：有些函数太长，长到没人能一次读完、改动时只能靠搜索。专业叫法：**Long Method / Cognitive Overload**（Fowler《重构》的长函数；McConnell《代码大全》第 7 章）。为什么值得知道：函数的长度和它的改动风险是直接挂钩的，越过一定长度以后，改的人不再"理解后修改"，而是"照着模式找到相似的一行然后复制"，历史事故大多发生在这个环节。

### 🔴 R1-1 `parseSmart` 705 行，把十套语法揉在一个函数里

- **证据：**

- **证据：**

- **后果：** 171 个调用点意味着**任何一次数据变化都会重建整个 `#view`**，代价是每次都跑一遍 `afterRender()` 的六个收尾（`applyHelp / observeReveals / syncStripFades / syncSegPills / syncTabDots / updateStatJump / __syncBarFit / syncFocusStrip`）。项目为此发生过至少两次同型事故：0G 的统计子页整屏空白（`statGo()` 是第二个渲染出口、漏了收尾），7.1.2 的点选整页闪（点一张卡走 `refresh()` 重播全部入场动画）。两次的修法都是"再补一条路"，而不是减少出口。

## 四、R2 变更传播

> **这一段在说什么。** 大白话：改一个地方，有多少别的地方会跟着坏。专业叫法：**Change Propagation / Shotgun Surgery / Hyrum's Law**（Fowler 的散弹式修改；Hunt & Thomas 的"正交性"；Winters 等《Software Engineering at Google》第 1 章的 Hyrum 定律）。为什么值得知道：改动的传播半径是可以量的，量出来之后就能判断"该不该先修结构再开发新功能"。

### 🔴 R2-1 交互总线的放大半径：一个按钮牵动四个必须同步的施法点

- **位置：** `鱼事.html:14602-15258`（委托）、`13478`（refresh）、`13564`（afterRender）、`15758`（refreshAfterChange）、`19277`（goView）
- **症状：** 加一个新交互，作者必须同时记住五件事：分支要插在正确的 `closest()` 顺序位置、要调 `save()`、要选对三个渲染入口之一（`refresh` / `refreshAfterChange` / `statGo`）、要确认新 DOM 片段有没有挂 `rv()` 揭示、要确认新元素在 `.reveal-on-scroll` 的 `pointer-events:none` 规则下点得动。
- **证据：** 三个渲染出口的存在是被文档化的历史事故：
  ```
  13559: /* ★ 0G：refresh() 的**渲染收尾** —— 抽出来给第二个渲染出口共用。
  13563:    收尾只留**一处**：以后再加渲染入口，调 afterRender() 就不会漏（不要再让调用点自觉）。*/
  13564: function afterRender(){
  15758: function refreshAfterChange(dur){
  ```
  但第三个出口是在 3B 才被发现的（记忆条目：`refreshAfterChange` 不经过 `afterRender`，漏它的症状是"清单页改完一条后顶部那行还停在上一帧"）。`afterRender(` 现在 6 处调用点。
- **后果：** 这类"忘了接第三个出口"的 bug 表现是静默的（元素在、命中正常、就是看不见或不同步），项目为此付出过至少三次完整排查：0G 空白屏、3B 焦点条不同步、7.1.2 点选闪。修补方式一直是"再加一处调用"，因此每加一个新渲染出口就多一次复发机会。
- **修法：** 收敛出口数量本身：让 `refreshAfterChange` 与 `statGo` 都走 `renderCurrentView() + afterRender()`，只保留 `refresh()` 一个公开入口，快慢路径由参数决定（`refresh({fast:true})`）。属**要动架构**，需要用户拍板，因为 171 个调用点里有一部分依赖 `refresh()` 的 rAF 合并语义（`rafRefresh`）。

### 🟡 R2-2 权限这一条知识写在四个地方

- **位置：** `_android/app/AndroidManifest.xml`（不含 INTERNET 的 n 条）、`_android/build.py:367-386`（按 `<uses-sdk>` 锚点注入 INTERNET）、`_android/_tools/verify_apk.py:131-145`（`EXPECT_PERMS` 硬编码集合 + 联网版/纯净版分支）、`鱼事.html:6385-6565` 与 `15174-15203`（页面侧能力探测与授权文案）
- **症状：** `verify_apk.py` 的断言是**集合恰好相等**（`got == EXPECT_PERMS`），所以任何一次权限增删都必须同步改它，否则核验必红。
- **证据：**
  ```python
  # verify_apk.py:131
  EXPECT_PERMS = {'android.permission.RECORD_AUDIO', 'android.permission.VIBRATE', …,
                  'android.permission.POST_NOTIFICATIONS',
                  'android.permission.RECEIVE_BOOT_COMPLETED',
                  'android.permission.SCHEDULE_EXACT_ALARM',
                  'android.permission.USE_FULL_SCREEN_INTENT'}
  147: check('权限恰好为 ' + repr(sorted(EXPECT_PERMS)), got == EXPECT_PERMS, …)
  ```
  项目记录里这条耦合已经咬过一次：4C 加精确闹钟两条权限时，核验脚本不在任务卡的写入范围内，"不改它卡里的收尾永远过不了"，最后做了最小改动。
- **后果：** 权限是安卓最容易出安全问题的面（须知第三节明确要求审 exported 组件、JS 桥、明文流量）。现在"系统实际声明了什么"与"核验脚本认为应该声明什么"是两份独立的真相，二者一致只靠人记得同步。一旦忘记，核验会红（安全的失败方向），但开发者为了过闸门最可能的动作是**改核验脚本**，这会把差异合法化。
- **修法：** 让核验脚本从 manifest 派生期望集合（解析 `uses-permission` 并断言与构建参数一致），而不是维护第二份清单；额外维护一份"必须存在/必须不存在"的短名单（如 `INTERNET` 按包型、`CAMERA` 必须不存在）。属**可安全修**。

### 🟡 R2-3 主源码有 35 个程序化写入者，其中 31 个是一次性补丁脚本

- **位置：** `_ref/_7f2-patch.mjs` 至 `_ref/_7f2-patch31.mjs`（31 个）、`_ref/_g13-fix.mjs`、`_g13-fix2.mjs`、`_g13-fixtest.mjs`、`_ref/_sync-build.mjs`
- **症状：** 这些脚本用 `fs.readFileSync('鱼事.html')` + `indexOf('某段源码字面量')` + `slice` 拼接 + `writeFileSync` 的方式直接改写主源码。
- **证据：**
  ```js

- **修法：** 把已应用的补丁脚本移出可执行位置（`_ref/_archive-patches/` 或删除，git 历史里已有），并让残留脚本在锚点找不到时 `process.exit(1)` 而不是打日志继续。属**可安全修**。

### 🟡 R2-4 原生桥的能力探测散在 20 多处

- **位置：** `鱼事.html:6385`（`notifyBridge()` 适配器）以及 `6386`、`6394`、`6417`、`6427`、`6436`、`6441`、`6449`、`6480`、`6545`、`6555`、`15174-15203` 等
- **症状：** 页面侧已经有一个"取桥并判 notifySchedule/notifyCancel 存在"的适配器（`6385`），但每个桥方法仍各自写一遍 `typeof b.xxx !== 'function'` 守卫。全文件显式 `typeof … === 'function'` 守卫 39 处。Java 侧 `YuShiBridge` 暴露 30 余个 `@JavascriptInterface` 方法。
- **证据：**
  ```

## 五、R3 知识重复

> **这一段在说什么。** 大白话：同一件事的规则，被抄在了好几个地方，改的时候只改一处就出事。专业叫法：**Knowledge Duplication**（Hunt & Thomas《程序员修炼之道》的 DRY，指的是"决策"而非"代码行"；Ousterhout《软件设计哲学》第 5 章的 Information Leakage）。为什么值得知道：这个项目的记忆里反复出现同一个句式的缺陷（统计口径、逾期口径、宽度基准、时间解析），它们全是"同一决定写在多处，然后某处忘了跟着改"。

### 🔴 R3-1 逾期口径 `due` 被逐字符抄了 5 份，而"唯一实现"是死代码

- **位置：** `鱼事.html:6747`（卡片染色）、`6942`（统计子页 `statPageHits('overdue')` 注释与实现）、`7419`（`chipDate`「逾期 N 天」）、`7504`（时间轴「其中逾期 N 条」）、`9204`（统计子页实现体）；另有 `7473` 的 `function itemDue(it)` 与 `7500-7503` 的说明注释
- **症状：** 同一行三元表达式在五处逐字符相同：
  ```js
  const due = (it.dateEnd && (!it.date || daysFromToday(it.dateEnd) >= daysFromToday(it.date))) ? it.dateEnd : it.date;
  ```
  项目已经建了唯一实现 `itemDue()`（`7473`），但它在全文件**只有定义、没有调用点**。`7500-7503` 的注释解释了原因：
  ```
  7500: /* ⚠️ 这里**故意**写 `const due = …` 那份三元表达式、不调 itemDue()：
  7503:    反而会把计数打乱（`itemDue` 是给"不想再抄第 5 份"的地方用的）。 */
  ```
- **证据：** 测试把副本数量写成了断言。
  ```js
  // _ref/_5g-regress.mjs:130
  const DUE_LINE = 'const due = (it.dateEnd && (!it.date || daysFromToday(it.dateEnd) >= daysFromToday(it.date))) ? it.dateEnd : it.date;';
  // _ref/_5g-regress.mjs:136
  t('那一行 due 表达式逐字符相同的处数（itemHTML / statPageHits / chipDate / 时间轴 / 7.2.2 逾期文案）', n, 5);
  ```
- **后果：** 复制不再只是习惯问题，而是被测试固化成了规范。新人在 `7503` 读到"`itemDue` 是给不想再抄第 5 份的地方用的"这句话时，会理解为"这里就该抄"。一旦有人真去改 `itemDue`（例如给区间脏数据加一条新规则），五份副本会保持旧行为，卡片染色与 chip 文案会与统计数字再次打架，而 `_5g-regress` 会同时报"份数是 4"和"某处行为不同"，问题描述的方式会指向测试而不是产品。
- **修法：** 让 `itemDue(it)` 成为唯一实现，五处全部改调它，并把 `_5g-regress:136` 的断言从"逐字符相同处数 = 5"改成"`itemDue` 的定义恰好 1 处 + 每个调用点都引用它"。属**可安全修**（行为等价，逐处替换，每处跑一次回归），但必须先改测试断言，否则改代码会红。

### 🔴 R3-2 测试夹具反向支配生产代码：四处"不许调用自己的真相源"

- **位置：** `鱼事.html:7269-7294`（`renderZoneBody` 里的统计口径）、`7500-7503`（`due` 副本）、`5857-5879`（提醒转发口）、`13586-13587`（`afterRender` 收尾守卫）、`10817/12645/15672/16221`（`const defer` 四处转发口）
- **症状：** 生产代码里有多处注释明说"这里不能调用正确的那个函数，因为纯 Node 回归脚本会把这段切出来喂桩"。
- **证据：**
  ```
  7289:      ⚠️ 这里**不能改调** statPageHits / statRootHits：0B 的纯 Node 回归把 renderZoneBody
  7290:      整段切出来喂桩跑，引用一个没桩的全局会直接 ReferenceError，把它一批本来绿的断言一起
  7291:      带走。两处口径相等由 _0e-regress.mjs 的运行时等式断言钉住
  ```
  ```
  13586:   /* ★ 3B：焦点条的收尾也挂在这里 … 纯 Node 回归会把 afterRender 单独切出去跑，
  13587:      那里没有 3B 这一块，所以守一道 typeof。 */
  13587:   if (typeof syncFocusStrip === 'function') syncFocusStrip();

  ```
  10817 / 12645 / 15672 / 16221:

  规模：全文件 `typeof … === 'function'` 守卫 39 处、`纯 Node` 注释 23 处、`隔离环境` 19 处、`转发口` 11 处。
- **后果：** 依赖方向被反转。正常情况是测试去适配生产代码的接缝；现在是生产代码为了迁就"把函数整段切出来跑"的测试方式，把自己的正确写法改成了次优写法。具体代价有两项：（a）**真相源分裂**，统计数字与渲染数字成为两份必须靠运行时等式断言维持同步的实现（一旦断言漏了新页面，就会静默漂移）；（b）**新功能成本上升**，任何"解析层函数要调用应用层新能力"都必须先加一个转发口，这是纯粹的仪式成本。
- **修法：** 把 `_ref` 的切片式回归改成两种之一：真正的 ESM 模块导出（需要把主文件拆成模块，用户拍板），或者在测试侧引入完整的全局桩表（`withGlobals({statPageHits, afterRender, …})`），让生产代码不必内联常量与守卫。属**要动架构**，需用户决策。
- **严重度依据：** Clean Architecture 的 DIP 说的是"高层不依赖低层细节"，这里是"生产代码依赖测试的加载方式"，属于结构性倒置。

## 六、R4 偶发复杂度

> **这一段在说什么。** 大白话：代码比它要解决的问题更绕，绕的那部分不是业务需要的，是历史上一个个小绕过攒出来的。专业叫法：**Accidental Complexity**（Brooks《人月神话》第 5 章的第二系统效应；McConnell 的 YAGNI；Ousterhout 的"战术编程 vs 战略编程"）。为什么值得知道：偶发复杂度和认知负载的区别在于，认知负载是"理解门槛"，偶发复杂度是"根本不该存在的东西"，后者可以直接删。

### 🟡 R4-1 两套事件模型并存

- **位置：** 1 个 657 行的 `#view` 委托（`14602`）+ 22 个局部 `addEventListener('click', …)`（`8211`、`9538`、`9744`、`12355`、`12583`、`13047`、`13461-13463`、`14227`、`14490`、`14590`、`14602`、`16471`、`16686`、`16697`、`16768`、`17238`、`17494`、`18170`、`18296`、`19392`、`19397`）；全文件 `addEventListener` 共 113 处

## 七、R5 依赖失序

> **这一段在说什么。** 大白话：谁该调谁，有没有绕回来。专业叫法：**Dependency Disorder**（Martin《架构整洁之道》的 ADP 无环依赖、DIP 依赖倒置、SDP 稳定依赖；Ousterhout 的信息泄漏）。为什么值得知道：依赖一旦成环，两个模块就不能单独理解、单独测试、单独替换，改动的代价变成"两边都要懂"。

### 🔴 R5-1 分区表子系统与应用层基座是真循环

- **位置：** `鱼事.html:6122`（`load`）→ `6150-6151`、`6156`（`sanitizeZones` / `migrateZones` / `zonePruneFolded` / `sanitizeZoneHints`，定义在 `4637`/`4715`/`4791`/滚动在 `4436-4802` 区间）；反向：`4623`、`4741`、`4752`、`4762`、`4775`（分区表的 `zoneHintClear`/`zoneAdd`/`zoneMove`/`zoneRename`/`zoneDelete`）→ `save()`（定义在 `6261`）
- **症状：** 应用层的装载函数调用分区子系统的校验与迁移；分区子系统的每个写操作调用应用层的持久化函数。两边都是同步直接调用，没有接缝。
- **证据：**
  ```js
  // 6150-6151（应用层 → 分区表）
  S.zones = sanitizeZones(o.zones);
  migrateZones(o);
  // 4741（分区表 → 应用层）
  S.zones.push(z);
  save();
  ```
- **后果：** 三项具体代价。（a）分区表不能单独测试：在隔离环境里调 `zoneAdd()` 会因为 `save` 未声明直接 `ReferenceError`，所以 `_7b-regress` 只能验纯函数，写操作一律要用真浏览器脚本。（b）`load()` 里那段顺序注释（`6141-6149`）记录了两次真实事故：先洗再迁会让老条目全掉进未分组；早先"先 `sanitizeItems(o.items)` 再迁移"导致迁移改了 `o.items` 而 `S.items` 还是空的。这两个坑都是循环依赖的直接产物：装载逻辑必须知道校验函数的内部副作用。（c）方向混乱意味着无法回答"分区表归谁"。
- **修法：** 给分区表子系统注入持久化回调而不是直接调 `save()`（`zoneAdd(name, persist)`），或者反向：把所有 `S.zones` 的写操作搬到应用层、让分区表只保留纯函数（`sanitizeZones` / `defaultZones` / `nextZoneKey` / `zoneHintsDropKey`）。后者更符合现状，因为纯函数那一半本来就是纯的。属**要动架构**，需要用户拍板。

### 🔴 R5-2 测试夹具与生产代码的依赖方向倒了

- **位置：** `鱼事.html:5857-5879`、`7269-7294`、`7500-7503`、`10817/12645/15672/16221`、`13586-13587`；对侧 `_ref/_0b-regress.mjs`、`_0e-regress.mjs`、`_2a-regress.mjs`、`_3a-regress.mjs`、`_3b-regress.mjs` 等 37 个使用 `new Function(` 的脚本
- **症状：** 测试用"切片 + `new Function` 隔离环境"的方式跑生产函数（`new Function(` 全 `_ref` 共 73 处，37 个文件），生产代码因此必须保证自己的片断在被切出来、放进没有 DOM、没有提醒层、没有应用层的环境里仍能运行。为此牺牲了：直接调用真相源（改成内联副本）、新建全局函数（改成内联常量）、引用应用层能力（改成转发口）。
- **证据：** 见 R3-2 引用的 `7289` 与 `13587`。另外 `5862-5867` 的注释把两个理由写得很清楚，其中第二条明确是测试约束：
  ```
  5864:      ② 已有的纯 Node 回归脚本（_ref/_0b-regress.mjs）是把 toggleDone 这类函数
  5865:         **按名整段切出来**、在一个隔离的 new Function 环境里跑的 —— 那个环境里没有提醒层。
  5866:         直接引用 syncNotify 会让它那 108 条本来全绿的断言整体崩掉，而任务卡明令
  5867:         不许改 _ref/ 下已有脚本。
  ```
  "任务卡明令不许改脚本"这一句是这个模式的关键：约束来自流程而非技术。
- **后果：** 每次加跨层能力都要付一次仪式成本（加转发口、加 typeof 守卫、把常量内联），而回报是"老脚本不红"。同时它让生产代码的**正确写法永远排在第二位**：只要测试切片的加载方式不变，真相源就会持续分裂。这是本报告里唯一一条"越改越差"的正反馈回路。
- **修法（两条路，都需用户拍板）：**
  1. **改造测试侧**：在隔离环境里注入完整的全局桩表，让生产代码可以自由引用跨层函数。
  2. **改造生产侧**：把主文件拆成真正的 ESM 模块（`parse.mjs` / `store.mjs` / `zones.mjs` / `render.mjs` …），构建时再打回单文件。这会把"单文件"从源码形态变成产物形态，是更大的决策。
  在两者都不做之前，至少把这类妥协集中记录在一处（例如 `_ref/COMPROMISES.md`），避免下一个人以为那是正常写法。

### 🟡 R5-3 分区 CRUD 被物理放在"解析层"切片内

- **位置：** `鱼事.html:4436-4802` 整个分区子系统，位于 `鱼事.html:4413`（标签词典）与 `鱼事.html:5881`（应用层标记）之间
- **症状：** 这一区间的注释身份是"解析层切片"，但里面装的是有状态的数据所有者（增删改分区、读写 `S.zones`、调 `save()`）。真正的应用层标记（`S` 的定义）在 `5888`。
- **证据：** `4454-4456` 的注释说明为什么常量放这里："纯 Node 回归脚本会把解析层整段切进隔离环境，所以这些必须落在那个切片里。"而 `4465-4469` 为 `zlist()` 加了 `typeof S === 'undefined'` 守卫，理由同样是测试环境里可能连 `S` 都没有。

- **修法：** 把分区子系统的纯函数（`ZONE_COLORS`、`ZONE_KEY_RE`、`sanitizeZones`、`defaultZones`、`nextZoneKey`、`sanitizeZoneKeys`、`zoneHintsDropKey`）留在解析切片，把写操作（`zoneAdd`/`zoneMove`/`zoneRename`/`zoneDelete`/`zoneHintClear`）搬到应用层。属**要动架构**（同时解决 R5-1）。

### 🟡 R5-4 AI 子系统按"开发批次"组织，不按层次

- **位置：** `鱼事.html:9900-10909`（标记为"AI（联网，独立可选）"）内含 `9900` 起的三块、`10124`（3.6 质疑）、`10160`（3.4 找关联）、`10228`（2A 理解内核）、`10495`（7B AI 落点）、`10576`（校验器）、`10666`（唯一入口）、`10760`（常用词采集）、`10825`（挂载建议接受拒绝）、`10872`（设置页动作）
- **症状：** 同一区间里既有网络调用（`aiCall` 在 `10017`，全文件唯一 `fetch`）、解析与校验（纯函数）、又有 DOM 操作与状态写入。

## 八、R6 领域模型失真

> **这一段在说什么。** 大白话：代码里的名字和用户嘴里的词对不上，或者本来该有行为的东西只是个装数据的袋子。专业叫法：**Domain Model Distortion**（Evans《领域驱动设计》的 Ubiquitous Language 与 Anemic Domain Model；Fowler 的 Data Class / Feature Envy）。为什么值得知道：名字一旦分裂，讨论需求和定位代码就会变成翻译工作，翻译过程中最容易丢的就是"这两个词是不是同一件事"。

### 🟡 R6-1 同一个概念有 4 到 5 个名字

- **位置：** 全文件（`kind:'seed'`、`zone:'idea'`、`sparks`、`S.noteMode`、`S.notes`、`notePage`、`ideaUI`、`noteUI`）
- **症状：** "想法"这个概念在代码里分裂成 `idea` / `seed` / `spark` / `想法` / `子想法` 五套词；"长文笔记"分裂成 `note` / `笔记` / `长文` / `草稿纸` 四套。
- **证据（去注释后的代码计数）：**
  ```
  idea 362 · Idea 14 · 想法 127 · seed 198 · Seed 107 · 种子 2 · spark 132 · sparks 80 · 子想法 7
  note 284 · Note 21 · 笔记 14 · 长文 21 · 草稿纸 4
  item 487 · 条目 42 · 待办 53 · task 27 · 任务 35
  zone 452 · 分区 70 · 栏 90
  ```
- **后果：** 这不是纯粹的命名洁癖，它已经产生过真实的理解偏差：项目记录里专门澄清过"种子卡片动作实际是 5 枚，`⧉合并` 在工具条上不在卡片上"、"卡片左侧是 `button.tick.seed-tick` 不是 `input[type=checkbox]`"、"`promoted` 是整条立项、`promotedTo` 是单步立项、`lastPromoted` 是时间轴入口"，这三条都是因为同一件事在不同位置用了不同的词，导致验收标准写错选择器或写错字段语义。另外「步骤」已经全站改名为「子想法」（记忆条目），说明这个词的漂移是被用户感知到的。
- **修法：** 定一份术语表并落到代码注释顶部：`seed` = 想法卡（`kind:'seed'`）、`spark` = 想法卡里的一步子想法、`note` = 长文笔记（`S.notes`）。改名成本高，至少先做到"新代码只用一套词"，并在 R6-2 的文档里建立映射。

### 🟡 R6-2 `S` 是被 802 处引用的贫血数据袋

- **位置：** `鱼事.html:5888` 起的 `S` 对象；全文件 `S.` 引用 802 处
- **症状：** `S` 持有条目、标签、分区、提示、笔记、主题、视图、筛选、折叠态、AI 锚点、行为学习、配额闸门等十几种状态；行为全部散在 515 个自由函数里，`S` 自己没有任何方法。数据形状的校验靠 `sanitizeItems` / `sanitizeParents` / `sanitizeZones` / `sanitizeNotes` / `sanitizeZoneKeys` / `sanitizeHotwordSeen` 这一串外部函数。
- **证据：** `S` 初始化字面量本身跨 `5888-5980` 左右，注释逐字段解释语义与迁移规则；顶层 `const` 122 个、`let` 60 个共享同一命名空间。

### 🟢 R6-3 "屏状态不进 S" 这条约定是清楚且被执行的

- **位置：** `鱼事.html:19282-19289`（`statPage` / `statFrom` / `notePage` 在 `goView` 里统一赋值与清理）
- **症状：** 无缺陷。项目明确区分了"要持久化的状态"（进 `S`、进备份）与"这一屏的临时状态"（模块级 `let`、不进备份），并在唯一入口里统一清理。

  19285:   statFrom = (v === 'stat' && o.from === 'list') ? 'list' : null;
  19289:   notePage = (v === 'idea' && o.note) ? o.note : null;

- **为什么值得保留：** 这是本项目在"领域边界"上做得最正确的一处，它把"临时状态"这个容易失控的概念收在了一个函数里。

## 九、测试资产（架构视角，T1–T6）

> **这一段在说什么。** 大白话：测试写得非常多（3,742 条断言），但没有一个统一入口，而且测试是通过"把源码剪下来一块再拼起来跑"的方式工作的。专业叫法：**Architecture Mismatch / Coverage Illusion / Test Brittleness**（Feathers《修改代码的艺术》的接缝模型；Google《How Google Tests Software》的测试金字塔；Meszaros《xUnit 测试模式》的脆弱测试）。为什么值得知道：测试是资产还是负债，取决于它是否保护了真实的风险点，以及它是否允许你重构。

### 🔴 T-1 3,742 条断言，没有 runner、没有 CI、一半脚本没进版本控制

- **位置：** `_ref/*.mjs`（224 个，2,789,887 B）；`.gitignore` 的 `_ref/` 一行；`git ls-files '_ref'` 结果 116 个文件（其中 `.mjs` 109 个）
- **症状：** 全仓库没有 `package.json`、没有 `.github/`、没有 `Makefile`、没有 `_ref/run-all.mjs`、没有 `_ref/README.md`。红线脚本清单只存在于会话记忆里。
- **证据：**
  ```
  total assertion-ish calls (t/tOk): 3742
  package.json: no    .github: no    Makefile: no    _ref/run-all.mjs: no    _ref/README.md: no
  _ref: tracked files = 116 ; files on disk = 1114
  mjs on disk: 224  tracked: 109  UNTRACKED: 115
  ```
- **后果：** 三项。（a）**不可复现**：换一台机器只有 109 个脚本，另 115 个（含 `_6d-shadow.mjs`、`_7d-regress.mjs` 这类在用脚本）会缺失，"回归全绿"这个结论无法在别处验证。（b）**漏跑无感**：29 个回归脚本 + 21 个 DOM 脚本要逐个手敲，没有任何东西会提醒你漏了哪个。（c）**反馈慢**：DOM 脚本要起 headless Chrome、跑一次几十秒到几分钟，全套跑完是分钟级以上的串行过程。
- **修法：** 先做最小可用的三件：写 `_ref/README.md`（红线清单 + 每个脚本一行说明 + 建议跑法）、写 `_ref/run-all.mjs`（按清单串行跑并汇总 PASS/FAIL）、把 `_ref/*.mjs` 从 `.gitignore` 放行（当前靠 `git add -f` 逐个维护，这是 115 个未跟踪文件的直接原因）。属**可安全修**，且收益最高。

### 🔴 T-2 断言钉在源码字面量上，重构就红

- **位置：** `_ref/_5g-regress.mjs:130-136`、`_ref/_6b-regress.mjs`（对 `_ref/_6b-baseline.json` 逐字符比 27 段处理逻辑）、`_ref/_7d-regress.mjs`（`grab()` 切片 `const AI_IMAGE_SYS`）、`_ref/_2c-regress.mjs`（去注释后源码级断言）、`_ref/_0e-regress.mjs` / `_ref/_7b-regress.mjs` 的源码级断言
- **症状：** 大量断言比较的不是行为，而是"某个字符串在源码里出现过几次"或"这段代码逐字符和快照一致"。
- **证据：**
  ```js
  // _5g-regress.mjs:136  把"复制了 5 份"写成期望值
  t('那一行 due 表达式逐字符相同的处数（itemHTML / statPageHits / chipDate / 时间轴 / 7.2.2 逾期文案）', n, 5);
  ```
  `_7d-regress.mjs` 的 `grab()` 曾因为新增一个 `const noteUI` 声明把切片长度从 23939 变成 11576 而假红（项目记录）。
- **后果：** 这是本报告里唯一一个"测试在奖励坏设计"的证据点：`_5g-regress` 的这条断言使得**消除重复会导致测试失败**，因此 R3-1 的修法顺序被迫变成"先改测试断言，再改代码"。同类问题的表现是"重构红一片、但功能没坏"，项目把这类一律称为"脚本漂移"，并在多次任务卡里记录了 8 到 21 条不等的一次性漂移修复。
- **修法：** 把源码级断言限制在两类确实需要的地方：（a）"红线必须只剩一处"这种唯一性断言（应改写成"定义恰好 1 处 + 每个调用点都引用它"，而不是"副本恰好 5 份"）；（b）对外契约的字面量（如 `data-capzone="auto"` 这类跨模块协议）。其余的改成行为断言。
- **严重度依据：** T2 的 Critical 判据是"无行为变更的重构导致测试失败、且有 5 个以上测试耦合到同一实现细节"。这里是"多处"，成立。

### 🟡 T-3 死代码靠测试存活

- **位置：** 与 R4-2 同（11 个函数只被 `_ref` 按名引用）
- **症状：** `_0e-regress.mjs`、`_7b-regress.mjs`、`_check-dupdef.mjs` 等脚本用名字清单把函数从源码里切出来，于是这些函数即便已经没有用户出口，也会因为"被测试引用"而显得有用。
- **后果：** 覆盖率的数字被这些不服务任何用户路径的函数撑高，让"覆盖率不错"这个印象失真（T5 覆盖幻觉）。同时它们给重构增加了无谓的连带修改面。
- **修法：** 对每个零引用函数先判断"是不是真的没有出口"（见 R4-2 的待确认项），确认无出口的一并从源码与测试清单里删掉。

## 十三、术语速查表

| 术语 | 一句话人话 |
|---|---|
| 认知负载 / Cognitive Overload | 一段代码要花多少脑力才能看懂 |
| 变更传播 / Change Propagation | 改一个地方，有多少别的地方跟着受影响 |
| 散弹式修改 / Shotgun Surgery | 一个小需求要跑到好几处零散的地方各改一笔 |
| 知识重复 / Knowledge Duplication | 同一件规则被写在好几个地方，改的时候只改一处就出事 |
| 信息泄漏 / Information Leakage | 一个模块的内部决定被另一个模块知道了，于是两者被绑在一起 |
| 偶发复杂度 / Accidental Complexity | 代码里那些不是业务需要、只是一路攒出来的绕 |
| 依赖失序 / Dependency Disorder | 谁该调谁的规矩乱了，比如上层调下层、或者两边互相调 |
| 循环依赖 / Circular Dependency | 甲要调乙，乙又要调甲，两边没法单独理解或单独测 |
| 依赖倒置 / DIP | 上层不该依赖下层的具体实现，应该依赖一个双方都认的接口 |
| 防腐层 / Anti-Corruption Layer | 在跨边界的地方放一个专门的转换层，避免两边的概念互相污染 |
| 贫血模型 / Anemic Domain Model | 数据对象只有字段没有行为，所有规则散在外面的函数里 |
| 统一语言 / Ubiquitous Language | 代码里的名字和用户嘴里说的词是同一套 |
| 上帝函数 / God Function | 一个函数包办了太多职责，长到没人能一次读完 |
| 事件委托 / Event Delegation | 不逐个元素挂监听，而是在外层容器上挂一个、靠事件冒泡统一处理 |
| 全量重绘 / Full Re-render | 数据一变就把整屏 HTML 重建一遍，而不是只改变了的那块 |
| 测试黄金标准 / Characterization Test | 改动之前先把"现在是什么行为"记下来的测试，用来防改坏 |
| 测试脆性 / Test Brittleness | 行为没变、只是重构了一下，测试就红了 |
| 覆盖率幻觉 / Coverage Illusion | 覆盖率数字好看，但真正会出事的路径一条都没测 |
| 源码级断言 | 断言查的不是程序行为，而是源码里某个字符串出现了几次 |
| 切片式测试 | 把源码剪下一段、拼成临时函数再跑，而不是 import 真模块 |
| Pain × Spread | 债务打分：现在有多疼 × 影响多大范围，乘出来的数决定先修谁 |
| 意外债务 / accidental debt | 没人故意留下的烂摊子，是慢慢积出来的 |
| 有意债务 / intentional debt | 当时明知而为之的妥协，一般有记录、有还的打算 |
| 健康分 / Health Score | 把发现折算成 0 到 100 的总分与分项，用来和自己历史比 |
