### [🔴] 恢复备份不校验 `aiBase` / `aiMode`：一份伪造的备份 JSON 足以把 API key 和待办内容发到攻击者端点

- 位置：`鱼事.html:18243`（恢复备份写 `S.aiBase`）、`鱼事.html:18242`（同批写 `S.aiMode`）、`鱼事.html:6209-6212`（启动加载同一处）、`鱼事.html:10018-10026`（唯一出网口 aiCall）、`鱼事.html:18196-18213`（drop 入口）
- 症状：`S.aiBase` 是外部数据（拖进页面的备份文件）可以完全接管的字段，而它直接决定 `fetch` 的目标地址；同一次恢复还能把 `aiMode` 一起设成 `full`。恢复后用户下一次录入，请求头 `Authorization: Bearer <用户的 key>` 与请求体（原话 + 最多 40 条未完成条目标题 + 常用词表）会整份发到备份里写的那个地址。
- 证据：
  - 恢复分支逐字段白名单里，其余字段都做了形状校验，只有 AI 三格是"是字符串就收"：
    ```js
    if (o.aiMode === 'off' || o.aiMode === 'title' || o.aiMode === 'full') S.aiMode = o.aiMode;
    if (typeof o.aiBase === 'string') S.aiBase = o.aiBase;      // ← 18243：任意字符串，无协议/域名白名单
    if (typeof o.aiModel === 'string') S.aiModel = o.aiModel;
    ```
  - 唯一出网口把它当成目标，并带上 key：
    ```js
    const base = String(S.aiBase || '').trim().replace(/\/+$/, '');       // 10018
    const res = await fetch(base + '/v1/chat/completions', {             // 10023
      headers: { 'Content-Type': 'application/json', 'Authorization': 'Bearer ' + aiKey() },  // 10026
    ```
  - 设置页的手写入口同样无校验（`鱼事.html:12071-12075`，`S.aiBase = v || 'https://api.deepseek.com'`）。
  - 与之对照，同文件的注释把这条控制写成了承诺：`鱼事.html:9911`「API key 单独存 … 备份 JSON 永不含 key」、`鱼事.html:12111` 界面上写着「API key（只存在这台手机上，不进备份文件）」。攻击面恰恰是"备份文件"本身。
  - 交付路径：drop 只要求文件里有 `items` 对象（`18196-18206`），确认框文案是「用备份里的 N 条，覆盖现在的 M 条？」——一份"帮你导出的待办备份.json"就能过。
- 后果：用户在"恢复我自己的备份"之后，API key（可计费、可冒充）与全部待办标题被静默转交给任意第三方端点；用户端没有任何提示，只有一次正常的录入。此后再打开设置页，接口地址那一栏就写着攻击者的域名。
- 修法：
  1. **`aiBase` 当成不可信输入收口**（唯一真相源放在一处，供 `load()` 与恢复备份共用）：只接受 `https:` 且 `new URL(x)` 能解析；对"非默认主机"给出明确确认（弹一句「接口地址会改成 xxx，模型服务商从此收到你的内容，确认？」），默认恢复为 `https://api.deepseek.com`。
  2. 恢复备份**不要**顺带恢复 `aiMode`（隐私开关的失败方向必须是"不联网"，与 `load()` 里 `S.aiMode` 那条回退口径对齐），或至少把 `aiMode` 的恢复加上同样的显式确认。
  3. 落库、发请求前在 `aiCall()` 里再判一次协议与主机（最后一道可信决策点）。
  4. 回归：给 `_ref/_0a-regress.mjs` 那类纯 Node 脚本加一条断言——备份里塞 `aiBase:'https://evil.example'` 时，恢复后 `S.aiBase` 必须仍是 `https://api.deepseek.com`。

### [🟡] 设置页「它学到的（分区）」把含用户数据的字符串未转义拼进 innerHTML（XSS 注入点）

- 位置：`鱼事.html:11851`（sink）、`鱼事.html:4610-4618`（`zoneHintText()` 拼串）、`鱼事.html:4646`（分区名上限 12 字）、`鱼事.html:4663-4676`（`g` 只限长度 ≤8、不限字符）
- 症状：`zoneHintText()` 的返回值里含**分区名**（用户/备份可写）与 **`S.zoneHints` 的键**（2-gram 来自条目标题，或备份直接写入），而它在设置页被原样插进 HTML：
  ```js
  <span>${zoneHintText()}</span>     // 11851
  ```
  `zoneHintText()` 返回的是 `'…「' + x.gram + '」→ ' + zoneNameOf(x.k) + '（' + x.n + ' 次）'`（4617），全程没有 `esc()`。
- 证据：
  - sink 侧无转义（`11851`）。同文件其它同类插值点都走 `esc()`，例如 `11847`、`11818`、`11819`、`6925`、`15543`、`17307`，说明这是漏掉的一处，不是既定写法。
  - 输入侧约束（决定了利用上限）：分区名 `sanitizeZones` 做 `replace(/\s+/g,' ').trim().slice(0, 12)`（4646）；`zoneHints` 的键只判 `!g || g.length > 8`（4668），**不判字符集**。
  - 本机实测（只读复算，未在浏览器里跑载荷）：12 字上限下能拼出的最坏形状是 `<img src=x>` 一类的未闭合标签（后续 `</span>` 的 `>` 会把它收掉，`onerror=` 无法在同一条属性序列里拿到合法值），**没有取得脚本执行的证据**。
- 后果：渲染结构被破坏（设置页那一栏错位/内容被吞）；配合 CSS 注入还可能篡改界面观感。若日后有人把分区名上限从 12 放宽、或把 `zoneHintText()` 换个插值位置，就会直接升级为可执行 XSS。
- 修法：`11851` 改成 `${esc(zoneHintText())}`（一次性）。纵深一步：`sanitizeZoneHints` 的 `g` 加字符白名单（例如 `/^[\u4e00-\u9fa5A-Za-z0-9_]+$/`），与 `sanitizeHotwords`（`9982`）同一套纪律——"外部数据不进内存当字段用"。
- **待确认**：要定性"能否脚本执行"，需要一份把 `zoneHints` 键与分区名同时拉到约束边界、并在真机 WebView 里跑 `elementFromPoint`/`onerror` 的探针；当前证据只能到"HTML 注入成立、脚本执行未证实"。

### [🟡] `android:allowBackup="true"` 且无 `dataExtractionRules`：API key、全部条目、笔记正文会进系统云备份

- 位置：`_android/app/AndroidManifest.xml:82`（`android:allowBackup="true"`，全 manifest 无 `fullBackupContent` / `dataExtractionRules`）
- 症状：应用界面与注释反复声明"key 只存在这台手机上、不进备份"，但**应用自己的备份 JSON** 与**安卓系统备份**是两回事。开着 allowBackup 且没有排除规则时，Auto Backup 会把应用私有目录整份同步到用户的云备份账号，WebView 的 localStorage（`daibanji.v2` 全部条目 + `daibanji.ai.key` + `daibanji.v2` 里的 `notes` 正文）与 SharedPreferences 都在其中。
- 证据：
  - `AndroidManifest.xml:82` `android:allowBackup="true"`；同日 manifest 里没有任何 `<full-backup-content>`/`<data-extraction-rules>` 文件（`_android/app/src/**/res/xml` 下不存在）。
  - 敏感落点清单（本机 grep 实证）：
    - `鱼事.html:6259-6291` `localStorage['daibanji.v2']` = 条目 + 标签 + 分区 + 常用词 + **笔记正文**（`notes: S.notes`，6290）；
    - `鱼事.html:9936` `localStorage['daibanji.ai.key']` = **API key 明文**；
    - `MainActivity.java:78 / 829-832` `SharedPreferences('yushi_notify')` 的 `t:<id>` = **待办标题明文**；
    - `鱼事.html:19462 / 14823` 另有 `daibanji.v2.theme`、LITE_KEY 两个小键。
  - 对照产品口径：`鱼事.html:12111`「API key（只存在这台手机上，不进备份文件）」；`_android/keystore/keystore.properties.example:5` 自己写明了"谁同时拿到密钥和口令谁就能签名"，说明作者是清楚备份面重要性的。
- 后果：换机/云恢复场景下，key 与全部私人待办（含长文笔记原文）随系统云备份离开设备；对"纯本地、不上传任何内容"的定位是实质冲突。
- 修法：在 `_android/app/src/main/res/xml/` 增加 `backup_rules.xml` + `data_extraction_rules.xml`，把 `app_webview`（localStorage/IndexedDB）与 `shared_prefs/yushi_notify.xml` 排除；manifest 的 `<application>` 上挂 `android:fullBackupContent` / `android:dataExtractionRules`。若愿意接受代价，`android:allowBackup="false"` 是最小改动。

### [🟡] 隐私告知与实际出网内容不一致：每次理解请求都附带最多 40 条未完成条目标题，界面只承诺"当前这一条"

- 位置：`鱼事.html:10447-10464`（实际组装）、`鱼事.html:10110` / `12108`（界面承诺）、`鱼事.html:11824-11825`（"发多少内容"三档的说明）
- 症状：界面文案写的是"鱼事会把**当前这一条想法的文字**发到模型服务商那里去"，而 `aiUnderstandUser()` 每次都会塞进 `S.items` 里**未完成条目的前 40 条标题**（`AI_LISTEN_MAX = 40`，`9926`）与整张常用词表。"发多少内容"三档只控制**当前条目**是否带原文/续写时间轴，不控制那张清单。
- 证据：
  ```js
  const list = S.items.filter(i => !isSeed(i) && !i.done).slice(0, AI_LISTEN_MAX)
    .map(i => '- ' + String(i.title || '').slice(0, 40));       // 10449-10450
  ...
  lines.push('--- 以下是背景，…');                                 // 10457
  ```
  对照 `鱼事.html:10003` 自己的注释「按隐私档组装要发出去的文本。**只发当前这一条**，不发全库。」——这句只对 `aiSeedText`（"问我一问"那条路）成立。
- 后果：用户按"只发标题 = 最保守"的选择，实际上每次录音/打字都把最近 40 条待办的标题一并送出；对这些标题内容的推断（健康、财务、人际）比"当前一条"敏感得多，且用户无从得知。
- 修法：二选一或都做——(a) 在三档下面加一行如实说明"为了判断挂到哪条下面，还会带上最多 40 条未完成条目的标题"；(b) 把这张清单做成独立开关（默认关），关掉时 `aiUnderstandUser` 不拼背景块，代价是"挂到哪条下面"要用户自己指定。

### [🟡] JS 桥 `readClipboard` 无调用方校验：任何在 WebView 里跑起来的脚本都能静默读走剪贴板

- 位置：`_android/app/src/com/yushi/app/MainActivity.java:1281-1309`（实现）、`218`（注册）、`鱼事.html:10066-10083`（唯一预期调用点）
- 症状：桥方法只做"读一次剪贴板"这一件事，native 侧没有任何"这一下是用户点的"的判断；注释里写"这是**用户点击触发**的读取"，但该保证完全由页面 JS 自觉。只要有任何一段脚本能在 WebView 里执行（现网未发现可用 XSS，见上一条），剪贴板内容（可能是密码、验证码、聊天内容）就能被一行 `YuShiNative.readClipboard()` 取走。
- 证据：
  ```java
  @android.webkit.JavascriptInterface
  public String readClipboard() {                    // 1282
      … cm.getPrimaryClip(); … out[0] = cs.toString();   // 1290-1294
  ```
  注册处只有名称约定，没有来源/手势校验（`218` `web.addJavascriptInterface(bridge, "YuShiNative")`）。
- 后果：当前无直接利用链（应用从 `https://appassets.androidplatform.net/index.html` 加载、只从 assets 取资源、不给外部页面导航，见下方"未发现问题"项），属纵深防御缺口：一旦注入面被打开，剪贴板就是现成的取数口。

### [🟡] 粘贴 key 后明文留在 DOM：遮字只靠 CSS，面板关闭前 `#aiKeyInput.value` 是完整 key

- 位置：`鱼事.html:10069-10076`（`fill` 里 `inp.value = s`）、`鱼事.html:12113-12115`（输入框标记）、`鱼事.html:4057`（遮字只靠 `-webkit-text-security`）
- 症状：`type=password` 被有意改成 `type=text`（理由充分：安卓安全键盘禁粘贴），遮字交给 `-webkit-text-security:disc`。于是粘贴/输入之后，`#aiKeyInput` 的 `value` 属性在 DOM 里是**完整明文**，直到面板被关掉（`closeModalNow` 清 `modal.innerHTML`）或用户点「显示」以外的路径失焦。
- 证据：
  ```js
  const fill = txt => { … inp.value = s; aiSetKey(s); refresh(); … }   // 10069-10074
  ```
  `refresh()` 只重画 `#view`，AI 面板住在 `#modal` 里（`12093-12104`），面板内的 input 不会因此被重建/清空。
- 后果：面板开着的那段时间，任何能在同源执行一次的代码（或用 USB 调试/开发者工具的人）都能直接读走 key——而 key 是长期凭据（可计费）。属于"把秘密留在可执行上下文里"的典型形状。
- 修法：`fill` 里改成不写 `el.value`，只调 `aiSetKey(s)` + `refresh()` 更新掩码（用户要核对后四位，label 上的 `aiKeyMask()` 已经足够）；「显示」按钮改成"临时把 value 写入 DOM 并 5 秒后清掉"，而不是长期驻留。

### [🟢] 全站没有任何 CSP（既无 meta 也无响应头）

- 位置：`鱼事.html`（`<head>` 见 `1-10` 行；全文件 `Content-Security-Policy` 零匹配）、`_ios/dist/index.html`、`MainActivity.java:1130-1138`（`respond()` 只加 `Cache-Control`）
- 症状：单文件应用靠 `esc()`（`5853`，覆盖 `& < > " '`）作为唯一注入防线。CSP 缺失意味着任何一处漏转义（例如上一条 `zoneHintText`）都没有第二道闸；`innerHTML` 一旦被注入 `<img src>`，浏览器会直接去取外部资源。
- 证据：grep `Content-Security-Policy|X-Content-Type` 全仓库 0 命中；`serve()`/`respond()` 设置的响应头只有 `Cache-Control: no-store`（`1132-1137`）。
- 后果：注入点的实际危害从"界面被搞乱"放大到"能向任意地址发请求"（在装着 INTERNET 的 AI 包里就是外发通道）。
- 修法：最低成本是给 `respond()` 的 `WebResourceResponse` 加一条 `Content-Security-Policy: default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data:; connect-src https://api.deepseek.com;`（注意：`script-src` 需要 `'unsafe-inline'` 因为全站内联脚本；至少把 `connect-src` 钉死能直接堵住"改 `aiBase` 外发"那一条）。PWA 侧同样在 `<head>` 加一条 meta。

### [🟢] WebView 未显式设置 `mixedContentMode`，只依赖默认值

- 位置：`_android/app/src/com/yushi/app/MainActivity.java:182-202`（WebSettings 全量设置段）
- 症状：`setMixedContentMode` 未被调用。当前行为安全（现代 WebView 默认 `MIXED_CONTENT_NEVER`），且入口本身是 https（`63`），但这是一条"靠默认值成立"的安全属性——未来有人为了兼容把入口改成 http，混合内容策略会跟着变。
- 证据：`182-202` 逐一设置了 JS/DOM storage/文件访问/文本缩放/强制暗色，唯独没有 mixed content。
- 后果：无当下影响；回归风险。
- 修法：显式加一行 `s.setMixedContentMode(WebSettings.MIXED_CONTENT_NEVER);`（API 21+）。

### [🟢] `jsStr()` 未转义 U+2028 / U+2029（现代 Chromium 已无影响）

- 位置：`_android/app/src/com/yushi/app/MainActivity.java:1227-1242`
- 症状：native → JS 的四个事件（`yushi:speech` / `yushi:notify`）都靠 `jsStr()` 做字符串字面量转义，它处理了 `" \ \n \r \t`，没有处理 U+2028/U+2029。ES2019 起这两个字符在字符串字面量里合法，所以当前 WebView 不会被打断。
- 证据：`1231-1238` 的 switch 只有五个分支；`emit()`（`1167-1175`）、`emitNotify()`（`1203-1207`）、`emitNotifyPerm()`（`1211-1215`）、`emitNotifyExact()`（`1220-1224`）四处共用它。
- 后果：无（若哪天降级到老 WebView 内核，`text` 里出现 U+2028 会切断 `CustomEvent` 的 detail）。
- 修法：switch 补两个 case（`\u2028` / `\u2029` → `\\u2028` / `\\u2029`），或直接改用 `JSONObject.quote(v)`。

### [🟢] SharedPreferences 里的待办标题明文且与页面数据双份

- 位置：`_android/app/src/com/yushi/app/MainActivity.java:78`（`N_PREF = "yushi_notify"`）、`829-832`（`putString(nKeyTitle(id), title)`）
- 症状：为了开机重排提醒，原生侧自己存了一份 `t:<id>` = 待办标题明文。这与页面侧 localStorage 是同一批内容的两个副本——删除条目的清理依赖页面调用 `notifyCancel`，历史上（5D）出现过"删了还响"的漏撤，也就是存在"内容已从页面删掉、原生副本还在"的窗口。
- 证据：`824-832`（`notifyPut`）、`675-676`（`notifyRemove` 才会清理）；页面侧删除链在 `鱼事.html` 的 `remove()` / `notifyReconcile()`。
- 后果：数据留存超出用户预期（页面上删掉的条目，标题可能还在 SharedPreferences 里）；配合 `allowBackup` 进云备份。
- 修法：标题不入 SharedPreferences（`t:<id>` 只存 id 与触发时刻，通知文案在 `ACTION_FIRE` 那一刻由页面进程补；拿不到就退回"+N 条提醒"这类中性文案）；并在启动对账时按页面数据清一遍孤儿键。

### [🟢] 分发渠道未公示产物哈希

- 位置：`README.md:60`（指向 `https://github.com/yurtin/yushi/releases/latest`）
- 症状：安卓侧靠签名天然防替换（installer 会拒绝不同签名的更新），但 README / Release 说明里没有 `sha256`，用户无法自查下载到的包与构建机产物是否一致——而项目里已经存在权威口径（`verify_apk.py:87` 会打印 SHA-256）。
- 证据：`_android/_tools/verify_apk.py:87-89` 输出 SHA-256；README 未附。
- 后果：无直接攻击面；供应链可核验性缺失。
- 修法：把 `verify_apk.py --ai` 打印的 sha256 写进 Release 说明（与记忆里"每次打包附 sha256"的既有流程对齐）。

### [🟢] `sanitizeItems` 对无 id 的备份条目用 `Object.assign({}, x, {id})`，`__proto__` 键会改写该条自身的原型

- 位置：`鱼事.html:6055`
- 症状：备份里一条没有字符串 `id` 的条目会走 `Object.assign({}, x, { id: uid() })`。`Object.assign` 用 `[[Set]]` 语义，若 `x` 带 `__proto__` 自有键（`JSON.parse` 会造出这种自有键），新对象的原型会被设成攻击者给的对象。
- 证据：全文件 21 处 `Object.assign` 已逐一核对，只有这一处的源是外部数据；目标是一个新鲜 `{}`，**不会**污染 `Object.prototype`。渲染层读取 `it.title` 等会走原型链，故"用原型提供字段"理论上可行，但能带来的效果不超过"多带几个字段"，且所有字段进 DOM 前都过 `esc()`。
- 后果：无越权后果（局限在单条对象自身）；属形状校验的边角。
- 修法：该行改成显式挑选字段（或先 `delete x.__proto__`），并给 `sanitizeItems` 加一条上限（条目数 / id 长度）。

## 术语速查

| 术语 | 一句话人话 |
|---|---|
| 信任边界 | 数据从"不可信来源"（外部文件、别的 App、网络）进入"可信程序"的那道门 |
| XSS / DOM 注入 | 把别人给的字当成网页代码来执行，或至少当成网页结构来解析 |
| `esc()` | 把 `& < > " '` 换成看得见但不会当代码用的写法 |
| PendingIntent 可变性 | 交给系统的"待办条"，别人能不能往里改内容（不能改 = IMMUTABLE） |
| exported 组件 | 其他 App 能不能直接拉起这个页面/接收器 |
| allowBackup | 安卓系统云备份会不会把应用私有数据整份抄走 |
| usesCleartextTraffic | 明文 HTTP 开关；关掉后本应用的 http 请求会被系统直接拦掉 |
| CSP | 浏览器端的白名单：规定页面只许从哪些地址取脚本/发请求 |
| ReDoS | 一条写坏的正则被一句话拖到卡死 |
| 原型污染 | 往 JS 对象共用的"祖先"上写字段，让全站对象都多出这个字段 |
| PWA / Service Worker 缓存 | 网页版给自己做的离线存盘，要注意别把秘密也存进去 |
