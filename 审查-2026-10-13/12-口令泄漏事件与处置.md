清洗后复扫：**0 文件命中**；抽查 UTF-16LE 日志仍可正常阅读（首行 `== 检查工具链 ==`）。

> 是历史上某次"UTF-16 误读再写回"的产物）。我的清洗只替换了口令那两处，其余字节未动，
> 没有让它变得更坏；该文件也从未被 git 跟踪。

## 五、教训（三条，建议写进流程）

1. **永远不要 `git add <目录>`**，只 add 明确列出的文件。
   本次 `git add 审查-2026-10-13` 把目录里的一切（含 `_tmp/` 下 14 个临时文件）都扫了进去。
2. **扫描敏感串必须覆盖三种编码**：UTF-8、UTF-16LE、UTF-16BE。
   "本地扫过一遍 0 命中"不等于干净 —— 第一版就是这么漏掉 53 个文件的。
   现成工具：`审查-2026-10-13/_pwscan.mjs`（`--apply` 可直接清洗，按编码分别写回）。
3. **会话转录 / 解压产物 / token 统计不属于仓库内容**，`.gitignore` 已封。

## 六、唯一的待定项：要不要换签名密钥？

**建议：不换。** 理由：

- 泄漏**从未离开本机**（未推送、未发给任何人），处置后本地对象库也已清净；
- 换 `.jks` 的代价是**已安装的用户无法再覆盖升级**（README 里写明了：签名变了，安卓会拒绝覆盖安装）——
  为了一个没出门的口令去牺牲全部存量用户的升级路径，不划算。

若你仍想要绝对安心，正确做法不是换密钥，而是
**给现有密钥补一条新口令权限更强的备份 + 把口令交给密码管理器保管**（密钥文件与口令分离存放）。
