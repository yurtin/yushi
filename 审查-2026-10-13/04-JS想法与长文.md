### [🔴] 批量删想法 / 清掉已收起的：撤销后父子关系**不可还原**（`sanitizeParents()` 就地改了共享对象）

- 位置：`鱼事.html:14934-14943`（`act === 'batchdel'`）、`鱼事.html:15095-15108`（`act === 'reviewpurge'`）、被共享的对象由 `鱼事.html:6098-6119` 的 `sanitizeParents()` 就地改写
- 症状：想法页多选 → 删除（或回顾抽屉里「清掉已收起的 N 条」）→ 点「撤销」。条目回来了，但**原来挂在这些条目下面的子想法全部变成了顶层**，层级永久丢失；`save()` 已把这个结果落盘。
- 证据：

  ```js
  // 14934-14943
  const keep = S.items.slice();                 // ← 浅拷贝：keep 里是同一批对象引用
  S.items = S.items.filter(x => list.indexOf(x) < 0);
  sanitizeParents();                            // ← 6116/6104 就地写 it.parent = null
  ideaUI.mergeMode = false; ideaUI.mergeSel.clear(); save(); refresh();
  toast('删掉 ' + list.length + ' 条', '撤销', () => { S.items = keep; save(); refresh(); });
  ```

  `sanitizeParents()` 的两处修正都是**就地赋值**：`if (it.parent === it.id || !byId.has(it.parent)){ it.parent = null; fixed++; }`（6104）、`if (bad){ it.parent = null; fixed++; }`（6116）。被它改掉的是"子想法"对象本身，而这些对象**同时**存在于 `keep` 里。于是撤销只把数组换回去，`parent` 字段早已是 `null`。
- 为什么这是"已经修过一次的同类缺陷"：5D 轮为单条 `remove` 专门补过"撤销要逐个写回 parent"（`鱼事.html:16288-16297`，`snap = tree.map(k => ({obj:k, parent:k.parent}))`）。**这两条批量路径没跟上同一处修复。**
- 后果：用户可见的表现是"删了又撤销，想法散架了"；而且因为 `save()` 已经写过盘，重开也回不来。触发前提是这些想法之间存在挂靠（`.seed-kids` / 拖到别的卡上挂靠都会产生 `parent`）。
- 修法（任选，建议 ①）：① 仿 5D —— 在 `sanitizeParents()` 之前把"将被牵连的 parent"记成 `[obj, parent]` 快照，撤销时逐个写回；② 把 `sanitizeParents` 改成**先返回修复清单再由调用方决定**（纯函数化），撤销时反向应用；③ 撤销不走 `keep`，改成"重插被删条目 + 重设 parent"两步（与 `remove` 的现有实现保持一致）。

### [🟡] `commitEntry` / `imageCommit` 的「撤销」不撤原生排期 —— 删掉的条目到点仍然响

- 位置：`鱼事.html:14439-14443`（录入提示条的「撤销」）、`鱼事.html:13037-13041`（图片入口的「撤销」）
- 症状：录一条**带日期或钟点**的条目（例：`3分钟后 吃药`、`明天9点 开会`）→ 立刻点提示条上的「撤销」。列表里没了，但原生侧那条闹钟**还在**，到点照样弹通知（点通知还会跳到一条已不存在的 id）。
- 证据：
  - `addItem` 落库时会排期：`notifyFire(it); dpKids.forEach(k => notifyFire(k));`（`鱼事.html:6696-6697`）。
  - 两处撤销都只改数组、**不碰提醒层**：

    ```js

    const tActs = [{ label: '撤销', fn: () => {
      const kill = new Set(ids);
      S.items = S.items.filter(x => !kill.has(x.id));
      save(); refresh();
    } }];
    ```

    ```js
    // 13037-13041
    toast('从图里加了 ' + made.length + ' 条', [{ label: '撤销', fn: () => {
      const kill = new Set(ids);
      S.items = S.items.filter(x => !kill.has(x.id));
      save(); refresh();
    } }], 9000);
    ```
  - 对照单条 `remove`（5D 定案）：**先 splice 再** `notifyFireMany(...)`，靠 `syncNotify` 的"不在库里 → 只撤不排"完成取消（`鱼事.html:16278-16285`）。这两处顺序与调用都缺。
  - 缓解因素（写清以免高估）：启动时的 `notifyReconcile()`（`鱼事.html:19566`）会把不在库里的排期清掉，所以孤儿闹钟**最迟在下次冷启动被清理**；爆炸半径是"同一次会话内、且触发时刻还没到的提醒"。
- 后果：用户眼中的"我撤销了怎么还响"，与 5D 修掉的"删了还响"是同一个抱怨。
- 修法：两处撤销改成 `const kill = new Set(ids); ...filter...;` 之后补一句 `if (typeof notifyFireMany === 'function') notifyFireMany([...kill]);`（不在库里 → 撤排期），与 `remove` 的写法对齐。
